# MXGA 功能回归

## 选用例

日常和发布前默认增量测试，从[脚本用例](tests/script/README.md)和[文本用例](tests/text/README.md)选择三类检查。同一检查命中多类时合并执行。

- **冒烟**选受影响功能最短的基本流程，例如改复制时先复制一条短帖。
- **迭代必测**默认选普通回复翻译往返 `GROK-01` 和搜索折叠原文复制 `COPY-03`。同一迭代可引用后续改动未影响的实测结果，验收时补齐。
- **变更点**测本次行为、相关边界和共享代码的调用入口。例如短链解析改动同时测点击和复制。

脚本用例和文本用例都可用于这三类检查。按用户指定的范围执行：「只跑受影响用例」只选相关用例，「某功能所有页面」逐页测该功能。只有明确要求项目全测时，才覆盖全部用例及本次变更点。仅改文档时核对规则、命令和链接。

## 通用验证规则

1. **先定义正确。** 以用户本次明确的需求为准，旧用例与之冲突时更新对应预期。其余行为沿用已有通过条件。AI 用已确认的样例或应沿用的 X 原生行为作独立对照，仍有歧义时再问用户。
2. **确认用例能抓住原来的错。** 能复现时，用同一检查验证修前失败、修后通过。功能和测试一起修改时，核对原有断言仍能识别该错误。
3. **动态内容用同一次结果比对。** 以当次页面状态为准。例如复制 Grok 译文，直接与这次显示的译文逐字核对。

## 脚本、AI 和人的分工

1. **脚本执行固定检查。** 有稳定预期和现成脚本时，按编号运行。例如复制外链后，直接比对剪贴板里的完整网址。
2. **AI 执行文本用例。** 自动化成本高、依赖特殊条件或需要观察界面效果时，直接按步骤实测，符合预期即记通过。重要流程有改动或用户反复反馈时，AI 也要走一遍受影响的操作，优先选已有的关联用例。例如脚本核对三段视频的位置，AI 在 Typora 中逐段点播放。
3. **人处理待决事项。** 需要授权、补充条件或作体验取舍时，AI 先完成能做的测试，再给出样本、已尝试的操作、实际结果和待决问题，由用户决定是否亲自复测。

## 执行

Chrome 实测复用已连接的 `my-chrome`、登录账号和[样本入口](references/samples.md)。Chrome 脚本在同一会话串行运行，关闭测试标签页后恢复原标签页。复制操作会写入 macOS 系统剪贴板。验证工作区改动前重载当前仓库的本地扩展，默认来源为 `UNPACKED`。验证商店版时指定 `MXGA_TEST_SOURCE=FROM_STORE`。来源不符或多份同时启用时记录为未验证，保留用户的扩展设置。

在仓库根目录按编号运行，例如：

```sh
node --test --test-concurrency=1 --test-name-pattern='^\[COPY-03\]' skills/mxga-regression/tests/script/post-copy.test.cjs
```

首屏或滚动性能有改动时，在同一 Chrome 版本、页面和操作下比较前后耗时，并按发起方核对新增请求。真实关系或反馈变更只在授权范围执行。

## 结果与清理

用例库中的测试按编号记录入口、版本与来源、实际结果及结论。脚本检查和 AI 观察各记实际测到的结果。缺少前提时标明未验证的步骤，继续执行其他用例。引用本轮旧结果时注明来源。

脚本异常时，AI 在同一样本上沿操作路径找出第一处差异。保留首次失败和复现条件，处理后只重跑受影响用例。原样本或等价样本须覆盖原触发条件，复测通过才记为已修复。其他样本通过时单独报告，原问题标为「修复效果未验证」。脚本与 AI 实测结论不一致时分别记录。

为测试启动前端、后端服务或其他后台进程时，记下对应的任务或进程 ID。测试完成、失败或中断时，停止本次启动的进程并确认已退出。测试前已运行、由本次复用的服务继续运行。

将本次产生的一次性脚本、截图、日志、导出文件和 Typora 测试文稿移入系统废纸篓。保留交付文件和长期回归资产。

## 维护

- `tests/script/` 放可执行用例。按任务选用 Shell、SQL、CJS、Python 等，优先复用现有脚本。一个脚本对应一类功能。每个测试函数对应一个用例，如标题 `[COPY-03] …` 对应 `test_COPY_03`。SQL 等可直接用编号标识独立检查。在索引中写清执行入口和通过条件。
- `tests/text/` 每类功能一个 Markdown 文件，每条用例用编号和名称作标题，写明前提、步骤和预期。README 只列功能和用例入口。
- 新增用例时，脚本和文本共用各功能的编号序列，取下一个未使用的编号。索引、用例和测试结果使用同一编号，换标题、换样本或切换执行方式时保留原编号。

用户明确要求发布时，对照本版改动和实测记录，把已验证的新功能收入用例库，已有行为更新原条目。对反复出现的误判，补入能识别它的条件，例如从用户报告的页面入口验证布局。补充可复用样本，列明新增、更新、已覆盖和待验证项，按需要选入冒烟或迭代必测。
